Support

Need help with a website refresh, product launch page, or a cleaner digital experience for your brand? We support businesses that want more clarity, stronger messaging, and smoother user journeys across their web presence. Use this page to describe an existing project question, an issue you can reproduce, or a change you need help planning.

Tell us what you're working on, what you expected to happen, and what happened instead. Include the affected page, device or browser, and any deadline that changes the priority. We can use that context to understand the request and discuss an appropriate next step; this form does not promise an emergency response or a particular resolution time.

Share evidence safely

Useful context should not expose private data

Support requests are easier to assess when examples are specific and sensitive details are removed.

  • Use a public URL or a short description if the affected page is private.
  • Redact names, email addresses, payment details, tokens, and customer records from screenshots.
  • Never submit passwords, API keys, recovery codes, or private account credentials through this form.
  • Describe impact and urgency without including information that should remain confidential.
  • If secure access is needed, agree on an approved method with the project contact instead of pasting credentials into a message.

Support request questions

Know what to expect before you submit

What information helps you reproduce a website issue?

Include the public page URL, the steps taken immediately before the problem, what you expected, and what actually happened. Note the device, operating system, and browser if you know them, and mention whether the issue occurs every time or only under certain conditions.

For visual or interactive issues, a screenshot or brief recording can help, provided private information is removed. Avoid sending account passwords or customer data. If the issue is intermittent, note when it occurred and any relevant non-sensitive error message.

Try to describe the shortest sequence of actions that shows the problem and whether it affects one page or several. If you can safely compare another browser or device, include what changed; do not attempt risky changes to a live system just to gather evidence.

Can I ask for a new feature or a redesign through support?

Yes, you can describe the improvement you are considering and the user need behind it. Requests that change the existing scope may require a separate discussion so the team can understand requirements, dependencies, approvals, and timing before estimating the work.

Explain who needs the change, what they should be able to do, and what happens today. If you are unsure whether it is a bug, a usability improvement, or a new feature, describe the behavior and the desired result; classification can be discussed afterward.

For a larger change, a separate project inquiry may be a better way to discuss goals, deliverables, review owners, and timing. That conversation can distinguish the immediate support need from follow-up work that requires a new scope.

Does submitting this form guarantee an emergency response or a fixed reply time?

No. This page does not publish an emergency service or guaranteed response-time commitment. Include the impact and any relevant deadline so the request can be understood, but do not rely on an unconfirmed form submission for urgent operational, security, or safety matters.

If your project has a separate support agreement or designated escalation route, use the contact method and process defined there. Never include passwords, secret keys, or sensitive records in an ordinary form submission.

For urgent incidents covered by an agreement, follow its escalation instructions and include only the minimum information those instructions request. If no emergency route has been agreed, do not treat this general form as real-time monitoring or incident response.

What if I do not know which service or category to select?

Select the closest available option or choose â€œNoneâ€ if the current choices do not describe the request. Use the message to explain the customer or team impact, what you want to happen, and what you have already tried.

It is more useful to provide an accurate description than to guess at a technical cause. The initial discussion can help determine whether the request relates to design, front-end behavior, hosting, content, or a different specialist need.

If you have a public page link, screenshots with sensitive details removed, or a clear example of the expected result, include it. Keep the message focused on the impact and avoid sharing information your organization would not normally disclose publicly.

What details should I include if the issue only happens sometimes?

Describe when you noticed the issue, how often it happens, the steps that seem to trigger it, and whether it affects a particular browser, device, page, or user action. Include relevant non-sensitive error text if available, but avoid guessing at the cause.

If behavior changes after a release or configuration update, mention the approximate timing and what changed. Do not make risky production changes to reproduce the issue; document what you can safely observe and let the project owner decide how to investigate further.

Include a safe example that shows the difference between a working and failing attempt, if one exists. Avoid repeatedly submitting forms or triggering transactions in production while testing, since that can create duplicate records or customer impact.

How should I report a possible security or privacy concern?

Do not post passwords, access tokens, customer records, or exploit details in this general form. If your project has an established private security-reporting or incident process, use that channel and follow its instructions for handling sensitive information.

State the general nature and impact of the concern without exposing private data. This support page does not represent a monitored security incident response service, so follow any organizational emergency or compliance procedures that apply.

Preserve relevant internal records according to your organizationâ€™s incident process, and limit further testing to activities you are authorized to perform. If a formal disclosure channel exists for the service involved, use that private route rather than publishing technical details.

What happens after I submit a support request?

The information helps clarify what is affected, how it impacts users or the team, and whether more context is needed. A request may need follow-up details or a separate scope discussion if it involves new functionality, multiple pages, or an external platform.

No fixed response time or resolution is guaranteed by the form. If you have an existing agreement, use its stated contact and escalation process. Keep a copy of the non-sensitive issue details so you can refer to the same steps if asked for clarification.

If the request involves a change rather than a defect, the next discussion may need to define scope, dependencies, and approvals before work can be scheduled. Keep the original report focused on impact so immediate triage is not obscured by unrelated ideas.

Can support help with content, accessibility, or performance improvements?

You can describe a content, accessibility, or performance concern and explain who it affects. Include the page, the task that is difficult, and any evidence you have, such as a customer report or a test observation. Remove private details from screenshots or recordings.

Some requests may require a broader audit, specialist evaluation, or separate project scope rather than a quick support adjustment. Clarifying the affected experience and desired outcome helps determine what kind of review would be appropriate.

For accessibility, describe the task and barrier rather than relying only on an automated score. For performance, include the page, device, network conditions, and any test context you have; different tools and environments can produce different readings.
